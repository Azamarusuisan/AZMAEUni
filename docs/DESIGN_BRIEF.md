# DESIGN_BRIEF — Note Draft Pipeline 導入・運用マニュアル
承認: ユーザー / 2026-07-31 / 版: v2

## 1. 主題
- 対象: Codex・Claude Code・Hermesで、記事制作を依頼から未公開下書きまで進めるAgent Skillの導入・運用マニュアル
- 読者: Claude CodeやCodexに興味を持って導入したが、まだ本格的な活用像を持てていない人。細かな実装より「結局、自分に何ができるようになるか」を先に知りたい。Windows購入者はPythonの版、PowerShell、OneDrive、WSL、会社PCの制約を自分で切り分けられない前提で案内する。主にPCで閲覧するが、スマートフォンでも結論を読めること
- 唯一の仕事: 読者が30秒以内に導入後の成果を理解し、「自分もこれを使いたい」と判断できるようにする
- 成功指標: ファーストビューとその直下だけで、入力、Skillが行う仕事、最終成果物、非対応範囲を説明できる。Windowsタブでは、購入者が一つのDoctorコマンドから環境固有の修正手順へ進める

## 2. 審査
- 最終判断者: ユーザー本人
- 過去のNG: 工程や技術の説明が先行し、導入すると何ができるようになるかという結論が目立たない
- 過去のOK: 現行マニュアルの落ち着いた配色、可読性、OS切替、実行例を残す
- 経由するレビュー: ユーザー本人の確認

## 3. 世界観
- 題材の固有物: 一行の依頼、調査メモ、記事原稿、アイキャッチ、未公開下書き、検証レシート
- ブランド人格: 技術を見せびらかさず、完了物を机の上に並べて説明する実務担当者
- 参照: 現行HTML — 落ち着いた編集マニュアルの体裁と可読性を継承
- 反面教師: 機能名や環境要件から始まり、読者が自分の成果を想像できない技術ドキュメント
- 業界の型: SaaS風の機能カード列挙は避ける。実際の「依頼→作業→成果物」を一つの仕事票として見せる
- 一次素材: 現時点ではスクリーンショット枠のみ。生成画像で疑似的な製品写真を作らず、正確なHTML図解と実スクリーンショットを優先する

## 4. トークン

### Color
既存のトークンを維持し、新色を追加しない。

- `--ink: #14201c` 本文
- `--bg: #ffffff` 地
- `--accent: #0f8a72` note・完了の強調
- `--brain: #a8620a` Brain固有
- `--warn: #b4472c` 禁止・未対応
- `--surface: #f6f8f7` 補助面

ダークモードも現行の対応値を維持する。

### Type
- Display: ヒラギノ明朝／游明朝 — マニュアルの編集物らしさを継承
- Body: ヒラギノ角ゴ／游ゴシック / 行長目安: 全角35〜45字 / line-height: 1.9前後
- Data/Caption: SFMono系 — 成果物名、状態、コマンドだけに限定
- 和欧混植: 現行のフォールバック順を維持し、見出しでは `text-wrap: balance` を使う

### Layout
- コンセプト: 「機能一覧」ではなく、テーマ一行が未公開下書き一式になる仕事票
- 密度: 中。最初の30秒は余白を確保し、既存の詳細マニュアルは高密度のまま残す
- ワイヤー:

```text
┌────────────────────────────────────────────┐
│ テーマを一行伝える                         │
│ 「○○についてnoteを書いて」                │
│                                            │
│ ↓                                          │
│ 調査 → 構成 → 執筆 → 画像 → CMS → 再確認  │
│                                            │
│ 最後に残るもの                             │
│ 未公開下書き / 原稿 / 画像 / 出典 / 検証記録│
│                                            │
│ できること ｜しないこと｜Brainの現在地     │
└────────────────────────────────────────────┘

以降：00 読み方 → 現行マニュアル
```

### Signature
- このページが記憶される唯一の要素: 「一行の依頼」が「未公開下書き＋ローカル成果物＋検証記録」へ変わる仕事票
- 理由: Agent Skillの価値はツール名ではなく、最後まで仕事が完了して検証可能な成果物が残ることにある

### Motion
- 予算: マイクロのみ
- 案: 「依頼→制作→成果」の経路を、ページ読込時ではなくユーザーが該当箇所へ来た時に現在位置として強調する
- 採用条件: 流れの理解を助ける場合のみ。`prefers-reduced-motion` では完全に静止
- 不採用: 全要素のフェードイン、装飾だけの線移動、スクロール追従

## 5. コピー
- トーン: 結論先行、具体、少しフランク。「何ができるか」を読者の依頼文と成果物名で示す
- 冒頭見出し案: 「『noteを書いて』で、調査から未公開下書きの保存まで終わる。」
- 補足案: 「最初に好みと文体を教えれば、次からはテーマを一行伝えるだけ。原稿・画像・出典・保存後の検証記録まで残します。公開ボタンは押しません。」
- 禁止語: 「シームレス」「次世代」「革新的」「可能性を解き放つ」「〜を実現」など、完成物を説明しない抽象語
- 確定原稿: こちらで叩き台を作り、実装後にユーザー確認

## 6. 禁止事項
- 冒頭をインストール手順、Python要件、機能名から始めない
- 3枚の汎用機能カード、絵文字アイコン、抽象グラデーション、生成された人物写真を使わない
- Brainの実機未確認機能を利用可能と見せない
- noteの公開、Brainの販売開始まで自動化すると誤認させない
- 「全部自動」のような安全境界を消す表現を使わない
- 現行の詳細情報を削除せず、冒頭から適切な節へ案内する
- 「すべてのWindowsで動く」と表現せず、Windows 11、Windows 10、WSL2、ARM64、会社管理PCの対応境界を明示する

## 7. 技術制約
- スタック: 単一HTML、CSS、最小限のJavaScript
- デザインシステム: 現行CSS変数を継承
- 対応幅: 320px以上
- a11y: ライト／ダーク双方のコントラスト、キーボード操作、意味的HTML、`prefers-reduced-motion`
- 画像方針: 生成画像は使わない。実画面のスクリーンショットが揃った場合だけ現実の証拠として掲載する
